# Dashboard page validation matrix

Static inventory of the 25 dashboard routes found in the Next.js build route table. All 25 anonymous routes redirected to their matching login callback; two navigations timed out but ended at the expected callback. The login accessibility snapshot showed the language selector, Welcome Back heading, Email and Password fields, Sign In, and Create account. The user-authorized login succeeded. In a fresh isolated context, authenticated rendering was confirmed for 22 pages using only route, heading, loading/error booleans, and text length; no data response bodies or chat/contact contents were inspected. A browser-local fetch guard blocked update-check POSTs during these route visits. The `/dashboard/chat` page and `/dashboard/chat/[jid]` both replace the configured `/wa-akg` URL with an unprefixed `/dashboard/chat...` path; reloading that path returned 404. A session-detail route with a nonexistent inert ID returned 404 for its session/monitor GETs and redirected to the sessions list; the real session-detail/QR view remains unverified. One update-check POST did complete during the fresh login before the per-navigation guard was applied; see the report's external-call caveat. No save, send, pairing, read/delete, or other UI action was triggered.

## Static test evidence and current limitation

The production build route table contains all 25 dashboard paths, and the root test suite includes `src/i18n/__tests__/messages.test.ts` and `config.test.ts`. Those tests validate locale catalogs, key parity, placeholders, ICU rendering, and locale resolution. They do not exercise dashboard components or provide page-level accessibility coverage. No dedicated dashboard component or accessibility test files were found under `src/**/__tests__`.

In the latest validation, Chrome DevTools exposed the existing authenticated local dashboard context. A guarded, read-only navigation pass attempted all 25 routes. The dashboard rendered; most subsequent route navigations timed out while Next compiled pages and still showed loading state, although limited heading snapshots appeared on several routes. Server logs showed 200 responses for sessions, session access, and an inert nonexistent session detail. During compilation of Settings, the dev process exited with code 134 after a V8 heap out-of-memory fatal error. Sticker, System Monitor, Users, and Webhooks then returned connection refused. The application is currently down. This pass did not perform UI writes, sends, pairing, or read/delete actions. The earlier isolated browser run remains the evidence for the 22 authenticated render checks recorded above; those checks did not verify write flows, full data states, or page-level accessibility beyond the login shell and limited headings.
